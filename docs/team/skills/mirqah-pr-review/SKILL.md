# مراجعة طلبات السحب (mirqah-pr-review)

المهارة المعتمدة لمراجعة أي طلب سحب (PR) في مستودع «فهرس مناهج التفسير» وفق المعايير الهندسية الصارمة للفريق.
المسار الإلزامي: **فرع نظيف ← فتح PR ← نجاح CI بالكامل ← مراجعة مستقلة عدائية عمياء** من وكيل/نموذج من شركة مختلفة عن المنفذ.

التفاصيل: [`references/checklist.md`](references/checklist.md) (قائمة التحقق التفصيلية) · [`references/branch-package-standard.md`](references/branch-package-standard.md) (معيار حزمة الفرع).

## بوابات المراجعة الأربع الإلزامية

### ١. حراسة البيانات المثبتة (ممنوع اللمس)
يُمنع منعاً باتاً تعديل أي ملف تحت `data/**/{raw,layers,spans,windows}`:
```bash
git diff origin/main -- data/
```
*يجب أن يكون الناتج فارغاً تماماً. أي تعديل في هذه المسارات يؤدي إلى الرفض الفوري (BLOCK).*

### ٢. إثبات الاختبار السلبي (Negative Testing)
كل إصلاح لعيب أو ميزة يجب أن يصحبه اختبار يفشل على `main` وينجح على الفرع. أوامر التحقق:
```bash
# التأكد من فشل الاختبار على الكود القديم:
git checkout origin/main -- src/
python -m pytest -q tests/test_new_fix.py

# التأكد من نجاح الاختبار على كود الفرع:
git checkout HEAD -- src/
python -m pytest -q tests/test_new_fix.py
```
*إذا نجح الاختبار على كود `main`، فهو اختبار شكلي ويُرفض الـ PR فوراً.*

### ٣. فحص حزمة الفرع الكاملة
التحقق من وجود الملفات الأربعة في `docs/branches/<branch-name>/`:
1. `HANDOFF.md`: ≤ ٨٠ سطراً، يتضمن طريقة الاستخدام الحقيقية وكيفية التحقق والمخاطر.
2. `SKILLS.md`: جدول المهارات ومصادرها.
3. `usage.html`: إنفوجرافيك 1600×900 بكسل، RTL، نص عربي خارج كتل الكود، بلا صور مولدة وبلا CDN.
4. `usage.png`: لقطة مولدة بـ Playwright (1600×900) بنصوص عربية سليمة وغير مقصوصة.

### ٤. فحص قواعد المنتج والصياغة (Product Rules)
- **منع النسب المئوية وادعاء الدقة:** لا تستخدم الرمز `%` أو `٪`، وأي رقم يُتبع بعبارة «أعداد توجيه وليست دقة».
- **منع ادعاء السبق:** تجنب كلمة «الأول» للسبق، واستخدم «في حدود بحثنا لم نجد...».
- **«لم ندرّب»:** الالتزام بعبارة «لم ندرّب نموذجاً بعد» وممنوع استخدام صيغة «درّبنا».
- **«وكيلان»:** الاقتصار على وكيلين في اللجنة (لا ثلاثة).
- **لا اعتماد آلي:** «اعتماد» محجوزة حصراً للمتخصص البشري.
- **لا مفاتيح في ملف أو شات:** المفاتيح عبر متغيرات البيئة فقط (`LLM_API_KEY`).
- **منع اختلاق النصوص:** كل نص قرآني أو تفسيري في الكود أو الاختبارات أو النماذج يجب أن يكون مقتبساً حرفياً من `data/**/spans`.
- **منع أسماء الأشخاص:** خلو كافة الملفات والوثائق والتعليقات من أسماء أي أشخاص.

## صيغة القرار الإلزامية (Verdict Format)

يُصدر المراجع تقريره مصنفاً الملاحظات بمستوى الأهمية والمسار والسطر:
- **P0:** حرج / يمنع الدمج (خرق قواعد المنتج، مساس بالبيانات، غياب الاختبار السلبي، كشف مفاتيح).
- **P1:** هام / يُعالج قبل الدمج (نقص في حزمة الفرع، خلل في التباين أو الوصول).
- **P2:** تحسين ثانوي.

```markdown
### حكم المراجعة: [PASS أو BLOCK]
- **المنفّذ**: [اسم الوكيل/النموذج]
- **المراجع**: [اسم الوكيل/النموذج المستقل]
- [P0/P1/P2] [المسار:رقم_السطر]: وصف الملاحظة الدقيق وسبل التصحيح.
```
